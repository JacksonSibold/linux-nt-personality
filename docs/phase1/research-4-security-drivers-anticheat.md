# Research 4 — Security, Drivers, Anti-Cheat, DRM, Services, Networking, Audio, Input, COM, .NET

**Status:** Phase 1 research report. Not authority (see `docs/phase0/DEFINITION-OF-DONE.md` §1).
**Scope framing:** Windows PE binaries execute as a native second personality on the Linux kernel
(Ubuntu 26.04 base). No user-mode Win32→POSIX translation server in the execution path; the
ARCH DoD constraints (≤1 personality syscall per PE launch; ≤0.05 host syscalls per NT call;
launch must survive killing every user-mode helper) are treated as binding design inputs.
Where a Windows component is legitimately a *user-mode subsystem on real NT* (SCM, LSA, COM,
audiosrv), implementing it in user mode is the faithful design, not a compatibility shim; the
prohibited pattern is user-mode translation of kernel ABI surface.

Classification used throughout:
- **DIRECT** — implementable on existing Linux facilities with our own code.
- **ADAPT** — existing Linux facility is close; needs a semantic/structural adapter, user or kernel.
- **NEW-KERNEL** — requires new kernel code (personality subsystem or extended core infra).
- **GATED** — final acceptance requires an artifact or decision controlled by a third party.

## 1. Windows security model → Linux mapping

### 1.1 What the Windows model actually is

| Component | Semantics that must be preserved |
|---|---|
| **SID** | Variable-length binary identifier (Revision + SubAuthorityCount + up to 15 32-bit authorities), well-known SIDs (`S-1-5-18`, `S-1-16-*` labels, `S-1-15-*` AppContainer), string form, authority/relative-ID composition. Not a number. |
| **Access token** | Per-thread object: user SID + N group SIDs + default owner + primary/impersonation type + privilege set (name, *present* vs *enabled* — two independent states) + integrity level label + AppContainer SID + capabilities list + restricted-SID list + elevation flags (`TokenElevationType`, linked token). Reference-counted, inheritable with filter rules. |
| **Security descriptor** | Self-relative or absolute SD: flags, owner SID, group SID, DACL (ACE list: ACCESS_ALLOWED/DENIED/_object variants, inheritance flags, propagation, callback ACEs), SACL (audit ACEs + mandatory label + policy ACEs). Canonical ordering rules; `SeSecurityDescriptorLength` etc. |
| **AccessCheck** | Kernel-side (`nt!SeAccessCheck`): generic→specific mapping via `GENERIC_MAPPING`, deny-then-allow ACE walk with STOP_ON_MATCH semantics, *object type* lists for ACCESS_ALLOWED_OBJECT_ACE, privilege-based grants (SeDebug/SeTakeOwnership/SeSecurity/SeBackup/SeRestore alter the check), primary-group handling, capability-SID checks against resource, *then* mandatory-integrity label check (no-write-up / no-read-up policy). Result is a granted-access mask, returned before handle creation — used by every executive object create/open path. |
| **Impersonation** | Thread token can be swapped to a client's token (SecurityAnonymous→…→SecurityDelegation levels); `SeImpersonatePrivilege` gates it; reverts on request end. Foundation of named pipes, RPC/DCOM, service clients. |
| **Privileges** | ~35 named privileges (`SeDebugPrivilege`, `SeTcbPrivilege`, `SeIncreaseBasePriorityPrivilege`, …) with distinct *effects wired into the kernel paths they govern*. |
| **Integrity levels** | System (0x5000)/High(0x3000)/Medium(0x2000)/Low(0x1000)/Untrusted(0), stored as a label SID in the token, enforced by mandatory policy in AccessCheck; per-object default from parent or explicit SACL label. |
| **UAC/elevation** | Admin token split into filtered (Medium, deny-only ACEs, disabled groups, `TokenElevationTypeLimited`) + linked full token; elevation is a user-mode broker (`consent.exe` + `svchost`/LSA policy) minting new tokens; Virtualization (File Manager VMStore, registry HKCU\Software\Classes\VirtualStore) for unmanifested Medium-IL writes to protected locations. |
| **Restricted tokens** | `CreateRestrictedToken`: disabled SIDs + restricting SIDs (SID that appears in a resource DACL as a deny-only "write restricted" pair → grants only if *all* restricting SIDs present on object) + level restrictions. |
| **AppContainer** | Capability SIDs (`inputInject`, `internetClientServer`, `privateNetworkClientServer`, …), per-appcontainer SID, default-deny network via WFP, broker token flow (`CreateAppContainerProfile` → `STARTUPINFOEX` PROC_THREAD_ATTRIBUTE_SECURITY_CAPABILITIES), object namespace isolation (`Global\`/`SessionN\`), UIPI IL enforcement for window message/input injection. |

### 1.2 Precise points where Linux uid/gid/capabilities are insufficient

1. **Identity cardinality.** Linux `cred` is one euid + ≤65536 supplementary gids + 40-bit capability set, per-task with per-thread capability inheritance quirks. Windows identity is a *list of SIDs of arbitrary authority* (multi-authority, non-numeric), plus a label, plus capability SIDs, plus restricting-SID sets. uid is not the user; the *token* is. No Linux field can hold a `S-1-5-21-…` membership list with semantics, and POSIX ACLs (even NFSv4-style xattr ACLs) lack: object-type ACEs, callback ACEs, inheritance *evaluation at create time with the exact propagation matrix* (INHERIT_ONLY/OBJECT_INHERIT/CONTAINER_INHERIT + no-propagate), canonical sort, and ACE-level audit flags.
2. **Privilege ≠ capability.** CAP_SYS_PTRACE is statically effective when permitted for root-ish operations; Windows privileges are *named, present-but-disabled-until-enabled, token-scoped, auditable*, and their effects are attached to the personality's own code paths (e.g. `SeDebugPrivilege` bypasses ACLs on *process* handles only at open time). Caps cannot represent "present but disabled", per-token privilege lists independent of the file-mode bits that set them, or the 35 distinct Windows effect mappings.
3. **No thread-granular token swap.** Linux has no in-kernel impersonation primitive; `SO_PEERCRED` transfers a *uid*, not a token; there is no reference-counted, inheritable, filterable credential object attachable to a request scope.
4. **No integrity/mandatory levels for native objects.** SELinux/AppArmor MLS can approximate (labels on tasks+inodes, MLS dominance), but the *policy language and decision outputs differ from NT's*: NT returns a granted-access bitmask (the caller then intersects `DesiredAccess`), while LSMs return yes/no per operation; `AccessCheck` must answer "what bits of this 32-bit desired mask are grantable, considering these generic mappings and object type GUIDs?" *before* the object exists (CreateFile DACL inheritance, `NtOpenFile` with `OBJ_INHERIT`). LSM hooks are not shaped for a mask-returning API, and reusing SELinux would collide with Ubuntu's shipped policy (LINUXR risk).
5. **Object namespace security.** `\BaseNamedObjects`, `\RPC Control`, `\Sessions\N`, `\GLOBAL??` — NT's object manager does the security on namespace lookups. Linux kernel has no comparable unified named-object namespace (keyrings are not it).
6. **Audit/SACL semantics**, **handle inheritance flags**, **`OBJECT_ATTRIBUTES`-sourced security**, **`SECURITY_ATTRIBUTES.Provider`**, and **secondary/`TokenDefaultDacl`/`TokenPrimaryGroup`/`TokenSessionId` information classes** all have no Linux analogue.

### 1.3 Proposed design

**Kernel (NEW-KERNEL):**
- **Personality token object** in the kernel object manager (owned by ARCH/NT domain, but the security blob is ours): token = SID blobs + privilege bitmap w/ enabled state + label + capability set + restricting SIDs + impersonation slot. Stored in `task->win_token` (reference-counted, LSM-free — this is a *personality object*, not a POSIX credential; Linux tasks get one lazily when a PE process runs). Linux-native processes never consult it; PE processes never have their POSIX `cred` weakened *or* strengthened — both credentials coexist (bridging rule in §1.4).
- **`winsec` kernel module implementing `SeAccessCheck`, SD parse/validate/canonicalize, SID compare** as exported in-kernel functions used by *all* personality object create/open paths (process, thread, file, section, key, base objects, IPC, WMI-lite). ~6–10k LoC; semantics fully documented ([MS-SDS], [MS-GLOS], [MS-ATA] + publicly known ACE behaviors).
- **SD storage**: personality objects carry SDs natively; files on ext4/btrfs get `security.nt.sd` xattr holding the raw NT SD (authoritative for PE world); bridge sync agent keeps `uid/gid/mode` ↔ SD primary-user/group/DACL-lite in sync (lossy both ways — declared in capability matrix). NTFS (if driver from FS domain lands) stores real SDs natively.
- **Impersonation**: kernel-internal `SeImpersonateClient` used by the pipe/ALPC/RPC personality transports (client token referenced on connect, thread slot swap, revert on IRP/completion end). NEW-KERNEL only in the sense of plumbing through our transports.
- **IL + AppContainer enforcement**: implemented inside `winsec` (label compare, capability-vs-`inputInject` gate on SendInput/window messages hooking into the window server, WFP hook for appcontainer network filter — see §6). Not via SELinux.
- **Restricted/elevation tokens**: pure token-filters in kernel (`CreateRestrictedToken` semantics including deny-only SID lists); UAC *broker* is user-mode (faithful: on NT, elevation is LSUASVC/consent user-mode + kernel `SeQueryInformationToken`/filter support).
- **Registry security**: our registry (REG domain) stores SDs per key, `REG_SET_VALUE`-style access checks in the key-path resolution — same `winsec` module.

**User space (matches NT layout):**
- `lsass`-equivalent: SID↔name (`LookupAccountName/Sid`), SAM-format local account store, LSA policy (privilege-user rights), package stubs (NTLM/Kerberos: interface-level only, see §1.5 trap list).
- `services`/`svchost`-style token derivation for §5; `consent`-style elevation UI.

**Classification:** token/AccessCheck/SD-xattr/impersonation plumbing = **NEW-KERNEL**; SID store, elevation broker, virtualization (VMStore) = **ADAPT/DIRECT user-mode**; whole scheme is **SELF** dependency class.

### 1.4 Non-negotiable Linux-safety rules

- Never map a Windows admin token onto `CAP_*` or uid 0. A PE process running "as SYSTEM" must have POSIX identity of the launching user (or a dedicated unprivileged `winpersona` uid), with all NT-rights semantics living inside the personality. Otherwise personality bugs become container/host escapes.
- Never weaken LSM/apparmor/seccomp profiles of Linux processes to "make Windows apps work"; security is added *on top* in the personality layer.
- Shared-file bridging must be *additive deny*: when a PE app asks the kernel for write access, both the NT SD *and* the POSIX check must pass (kernel already does POSIX at `filp_open`; `winsec` runs as an internal post-check). When a Linux user writes a file a PE app protected via xattr SD, POSIX wins (declared asymmetry; matches how Samba behaves as reference).

### 1.5 Known traps (SEC)

- ACE inheritance is applied **at create time from the parent's SD** and is then independent; `SetKernelObjectSecurity`/protected-child flags; `SE_DACL_PROTECTED`; container-vs-object inheritance masks for directories vs files.
- `SeBackupPrivilege`/`SeRestorePrivilege` bypass DACL *without* modifying access masks (open with `ACCESS_SYSTEM_SECURITY` etc.); backup semantics affect path traversal checks (open by file ID).
- Well-known SID table completeness (100+ constants; `S-1-15-2-…` capability SIDs are *computed* by hashing capability names — algorithm is public: SHA-based, must be byte-exact).
- Token information-class enumeration (`GetTokenInformation` has ~40 classes; several undocumented layouts — EXT-RE).
- Privilege *use* audit events and `TokenLinkedLevel`/`TokenOriginId`/`TokenIsAppContainer`/`TokenCapabilities` behavior on Win8.1+ vs 10+ (fingerprinting surface for ACs — §3).
- `SeAccessCheck`'s "access system security" (SACL read requires SeSecurityPrivilege, *silently* succeeds otherwise with `ERROR_PRIVILEGE_NOT_HELD` nuance), and `STATUS_ACCESS_SYSTEM_SECURITY` vs `ERROR_PRIVILEGE_NOT_HELD` reporting for `GetSecurityInfo`.
- Impersonation levels: SecurityDelegation requires actual credential forwarding support — return `ERROR_IMPERSONATION_LEVEL_NOT_SUPPORTED`-shaped failures rather than fake success (many apps treat delegation as a probe).

## 2. NT driver model — can `.sys` run natively in the Linux kernel?

### 2.1 The NT driver ABI (what "a `.sys`" actually is)

A `.sys` is a **kernel-PE image** (machine x64, `SUBSYSTEM_NATIVE`, no CRT assumptions) that exports `DriverEntry`; the loader calls it with `PDRIVER_OBJECT` + registry path string; driver then fills `MajorFunction[]` (IRP dispatch table, 28 slots), creates device objects (`IoCreateDevice` → `DEVICE_OBJECT` with its own dispatch table), publishes symbolic links and device interfaces (PnP, `GUID_DEVINTERFACE_*`), attaches to the device stack (filter drivers), and services IRPs (I/O Request Packets — chained structures with stack locations, MDLs, completion via `IoCompleteRequest` with priority-boost semantics, pending I/O, cancel safe stacks). Everything is governed by:
- **IRQL** (a *schedulability contract*, not CPU priority: PASSIVE ≤ pageable, APC, DISPATCH ≤ no-paging/spin-safe, SYNC_LEVEL, HIGH_LEVEL) — violation = bugcheck 0xD1; Windows tracks current IRQL per thread.
- **Executive APIs**: `ExAllocatePool*` (tagged pool types NonPaged*/Paged*/Nx/PerNode with quota + accounting), `Ke*` (events, semaphores, timers, DPCs, spinlocks, `KeWaitForSingleObject` with wait-block/`KWAIT_BLOCK` lists, APCs — `KeInsertQueueApc` with `KernelRoutine`!), `Io*` (MDL build/probe/lock, work items, registry, `IoBuildDeviceIoControlRequest`), `Zw*` (kernel-call gate), Rtl string/splay/LFH.
- **MSVC SEH**: x64 `.pdata`/`UNWIND_INFO` tables, `__try/__except` inside kernel functions, `KeBugCheckEx` from the OS side, `RtlVirtualUnwind`-based stack walking *by the driver itself* (AC/BattlEye walk kernel stacks).
- **Signing/CI**: DSE requires an EV+WHQL ("Microsoft Windows Hardware Compatibility Publisher") chain (or test-signing with attestation), verified by `ci.dll` (`CiValidateImageHeader`) at load; HVCI makes Secure Kernel flip NX on writable pages before making executable.

### 2.2 Rigorous feasibility analysis of native NT-ABI driver execution

**What is merely difficult (all engineering):**

| Requirement | Assessment |
|---|---|
| PE kernel loading | Solved in our loader domain: map image, apply relocations, validate. *Difficult*, not hard: kernel-mode mapping with W^X + per-module permissions; NX for pool. |
| Pool API | `ExAllocatePool*` → `kmalloc/kvmalloc` wrappers with pool-type→gfp mapping (NonPaged→GFP_ATOMIC-ish, Paged→allow-reclaim — but see IRQL), tags + quota + accounting; `ExFreePool` must honor `POOL_QUOTA` and the (real-Windows) double-free crash semantics we choose to emulate as `WARN` (do not panic the host: **hard rule** — personality driver faults must kill the driver, not Ubuntu; see risks R-DRV-1). |
| Executive objects (KEVENT/KSEMAPHORE/KMUTANT/KTIMER/KDPC) | We already need user-mode event/semaphore/mutant objects (ARCH/NT domain). Kernel drivers use the *same* object layouts and `KeWaitForSingleObject` — NEW-KERNEL but shared infrastructure: in-kernel waitable object runtime with NT status-returning wait + timeout + alertable semantics, priority boost emulation. |
| DPC model | Linux has tasklets/hrtimers/workqueues — none is an exact IRQL-pinned DPC. Implement a real DPC runtime: per-CPU queues, lockless `KeInsertQueueDpc`, DISPATCH-level context (preempt disabled + no sleeping — expressible today via `local_bh_disable`/`cant_sleep` + our IRQL var), timer linkage (`KeSetTimerEx`+`DeferWindowPos`-style DPC). *Difficult* (latency, migration), but fully in our control. |
| IRQL emulation | Per-thread `current_irql` in `task_struct` + enforcement in all wrappers (pageable pool at ≥DISPATCH → emulate `POOL_USE_QUOTA_AT_RAISED_IRQL` failure or *controlled* crash of the offending driver; `KeWaitForSingleObject` at ≥DISPATCH → `STATUS_INVALID_IRQL`… note: real Windows bugchecks, we must kill driver instead). Linux's *preemptible* kernel actually helps: PASSIVE-level context maps to preemptible code; blocking at PASSIVE is legal both worlds. The dangerous direction (driver sleeps where our wrappers allow but Windows forbids) is caught by our IRQL checks. **No fundamental blocker** — this is a discipline-emulating layer. |
| Kernel SEH/unwind | Drivers' `.pdata` must be registered in-kernel and a personality exception dispatcher built (raise→dispatch→unwind, `EXCEPTION_RECORD`/`CONTEXT` layout) *plus* `__try/__except` in *our* wrappers. Linux kernel has no unwinder tables (ORC is non-foreign-readable). Build: import `.pdata` into our own xarray, implement RtlVirtualUnwind equivalent (tables are standard format), route personality faults through it. **Hard engineering, no third party.** |
| Device manager / PnP / device stacks | Implement `\Driver\*`, `\Device\*`, `\SymbolicLink\*`, device-interface arrival/removal notifications (`IoRegisterDeviceInterface` + `CM_*`/`SetupDi` user-mode surface — DOD-DRV-A002 wants exactly this). New kernel subsystem; semantics well-documented. |
| IRP plumbing | `IoCallDriver`, stack locations, completion, cancel, `IoCompleteRequest(IOPRIORITY_INCREMENT)` boosts → map to our wait-runtime. Straightforward-but-large. |
| WDF/KMDF | `WdfDriverCreate` etc. live in `WdfLdr.sys`+framework — we can supply our own faithful WDF co-installers (the *contract* is documented; WDF is user of the NT ABI, so build NT layer first). |
| Signing gate | Our CI policy: test-signing CA (project-controlled) — DoD already mandates. We *can* additionally validate the MS WHQL chain (certs are public) — engineering; but see blockers below for why that doesn't help third-party `.sys` in practice. |
| NDIS/WDK class surfaces | Class drivers (diskclass, cdrom, net class) are MS-provided *drivers*; we must re-author them as personality components over Linux block/net — that is our code, fine. |

**The hard blockers (third-party production `.sys` on our kernel):**

1. **Undocumented internal ABI + build fingerprinting.** Serious binary drivers (GPU, AC, DRM, hypervisor-ish) bind to *ntoskrnl internals*: hardcoded `EPROCESS`/`_ETHREAD` offsets guarded by `ExBuildNtBuildNumber`/`PsInitialSystemProcess` identity, patch-scanning for `KiSystemCall64` patterns, `MmGetSystemRoutineAddress` on private names, ETW/LIBHAL internal functions (`HalCollectPmcCounters`-style hooks documented in Vanguard RE literature), dxgkrnl/WDDM private interfaces. Emulating "ntoskrnl.exe version 10.0.26100 with Microsoft's exact internal layout" is (a) unbounded (every driver pins something different), (b) a *copyrightable-expression* problem if byte-copied, and (c) a moving target per Windows build. **Blocker class: the driver's own assumptions, not signatures.**
2. **PatchGuard semantics.** Kernel ACs and some DRM verify PG is alive (watchdog thread signatures, `KiQueryIdleBranchTargetListHead`, bugcheck 0x109 self-tests). We *can* build an equivalent integrity watchdog, but any check that hashes *ntoskrnl image bytes* fails: our "nt" is not Microsoft's binary and we can't ship theirs. **Blocker (hash-of-OS-image checks) unless the checker only verifies *its own* presence/behavior.**
3. **VSM/HVCI co-design.** Drivers that call Secure-Kernel interfaces (`Sk*` secure calls, `GetRuntimeAttestationReport`, HVCI page-visibility) assume the Windows hypervisor + Secure Kernel exist — those are VTL1/VTL2 components of the MS platform. We could build an analogous (e.g. SEV-SNP/TDX + TEE-based) design, but *their* binaries speak to *MS's* components. **Blocker.**
4. **Stability-layer blast radius.** One misbehaving third-party driver = host kernel panic = violates "no Linux regression" absolutely. Until we have in-kernel isolation for personality drivers (hardware sandboxing is not available), shipping an unbounded third-party `.sys` surface is **architecturally disallowed by our own DoD**, independent of ABI feasibility. (User-mode driver-hosting via vfio/UIO is the containment path — but then it is no longer "native NT-ABI `.sys` in kernel", it's a re-hosted port: fine for *our* drivers, not for arbitrary ones.)

**Verdict:** Loading **our own NT-ABI `.sys` files natively in the Linux kernel is credible** and is the DoD-DRV-A002 path (virtual device stack, test CA, Toaster-class device model). Loading **arbitrary third-party production `.sys` is not credibly achievable**: blockers #1–#4 are not "more engineering" — they are assumptions about *being Microsoft's kernel* or artifacts only Microsoft/vendors can retire (by recompiling for us — a partnership outcome, GATED). The honest capability statement: "NT driver personality executes first-party and partner-built drivers; third-party kernel binaries are out of scope by technical blocker, with an attempt-matrix audit (DOD-DRV-A001/B005 already classifies this EXT-GATED)."

**Resolving experiment (cheap, decisive):** compile+load (a) Microsoft's public Toaster *sample* sources as real `.sys`, (b) a captured simple third-party virtual-device `.sys` (e.g. an old null/serial class filter) against a v0 executive shim; measure import-satisfaction rate (% of IAT thunks resolvable from documented export set) across a 200-driver corpus from Sysinternals/VxD-era archives → gives a numeric distribution for §2 claims.

### 2.3 Driver signing & code-integrity subsystem (CI)

Personality CI = our `ci.dll`-analogue: image certification (`CiValidateImageHeader`-shaped API for user-mode `WinVerifyTrust` too), catalog files (`.cat`, Authenticode hash formulas — [MS-AUTHODDIG], documented), chain policy (test mode vs production mode), revocation (our CRLs), **Secure Boot tie-in** already covered in BOOTPH (custom PK + MOK). `GetRuntimeAttestationReport` cannot be honestly implemented (see §3 K-12); `NtQuerySystemInformation(SystemCodeIntegrityInformation)` etc. return *our truthful* state (test-signed → flags set; ACs fail us — that's the gate, not a lie we should try to paper over).

## 3. Anti-cheat — first-class analysis, per-check table

Trust model summary (for the report's own conclusions): kernel AC exists because ring-0 cheats blind ring-3 AC; therefore AC checks split into (a) *locally observable behavior* — a faithful non-NT kernel **can** satisfy these by *being* what's claimed (we run on real metal, real TPM, real Secure Boot; our kernel genuinely enforces integrity); and (b) *crypto-attestable claims about the Microsoft platform* — these are unsatisfiable by construction because the artifact verified is produced by MS keys/structures we don't possess.

**Table legend.** (i) what it verifies; (ii) Satisfiable = can a non-NT kernel satisfy by faithful implementation? (Y/N/partial); (iii) Artifact = third-party-controlled artifact needed for *acceptance by the AC vendor's backend*, with party named; (iv) Best = strongest achievable outcome. Verdict: ENG=hard engineering (self), HYB=works locally but final acceptance is a vendor-policy decision, **GATED**=third-party-controlled artifact required.

### 3.3 Anti-cheat conclusions (go/no-go grade)

1. **User-mode-only AC titles** (many co-op/indie/midcore games, VAC-classic, older ACE/Xigncode UM modes): **credible full local engineering path.** Every UM check above is faithfully implementable by *being genuinely secure* (native exec, real TPM/Secure Boot, our own integrity enforcement, honest version persona). Residual risk: server-side heuristics treating the platform as unknown (K-13) and AC build-DB drift for SSN/version fingerprints (U-05/U-13). This matches DoD DOD-AC-003 (user-mode anti-tamper titles) being ungated.
2. **Kernel AC titles** (Valorant/LoL-Vanguard, FACEIT-CS, BE/EAC-kernel titles): **GATED, not closable by engineering.** Root cause is *not* signatures; it is that (a) their `.sys` cannot ABI-execute on us (K-01), and (b) the 2026 trust anchor for the biggest of them (Vanguard on-demand) is a **Microsoft Secure-Kernel artifact** (K-12). The only credible route is a **commercial certification program**: AC vendor rebuilds for a Microsoft-sanctioned-adjacent target = our platform, against our SDK/DSE, with our attestation report accepted by their backend. That is a business outcome. Report honestly: **kernel-AC compatibility is out of scope for engineering DoD; project-level decision = accept "competitive titles with kernel AC do not play" as a declared capability-matrix row.**
3. **Do not attempt spoofing.** Faking PatchGuard layout or K-12 report shapes is (a) detectable, (b) legally worse (DMCA §1201 circumvention optics), (c) self-defeating for our security posture. Faithful-implementation-or-honest-failure is the only policy to encode.
4. Our own **test-AC** (project-internal "Vanguard-class" driver using our personality kernel APIs + our attestation report + our fake server, end-to-end) is the right DoD-adjacent artifact: it proves the *mechanisms* (K-03..K-11 all green), and doubles as the SDK demo to court vendors.

## 5. Windows services (SCM)

**What must be faithful:** the SCM state machine (`services.exe`/`SVCHOST` + in-kernel nothing — on real NT the SCM is user-mode over the Service Control Manager dispatch; kernel only sees the session/process objects), `[MS-SCM]` RPC protocol (opensvc/startsvc/controlsvc/queries, handle table), service types (WIN32_OWN_SHARE/INTERACTIVE vs WIN32_SHARE_PROCESS vs SERVICE_KERNEL_DRIVER/SERVICE_FILE_SYSTEM_DRIVER → these last two route into *our driver personality* §2), service accounts (LocalSystem `S-1-5-18`, LocalService `S-1-5-19` w/ null DACL + restricted groups, NetworkService `S-1-5-20`, per-service SIDs `NT SERVICE\x` — SIDs synthesized by well-known algorithm), **session 0 isolation** (services in session 0, non-interactive, no window station visible to user sessions), start types + dependency graph (`SERVICE_AUTO_START`/`DEMAND_START`/`DISABLED`, `DependOnService`/`Group`, `WaitTimeout`, failure actions/recovery), autostart (`Run`/`RunOnce` registry + Startup folder), and the `StartServiceCtrlDispatcher` handshake (service main + status reporting `SetServiceStatus` with pending-state ticks — many installers poll this).

**Design:**
- Kernel contribution: **session objects** (`\Sessions\0\…`, `Winsta0\Default` cross-session visibility rules), token synthesis for the three built-in accounts, and the driver-service load path (SERVICE_KERNEL_DRIVER → our `.sys` loader). That's it — NEW-KERNEL items are small.
- User-mode: `services.exe` (our build, a personality process — *this mirrors NT's own architecture*, not a POSIX substitute) implementing [MS-SCM] over our LRPC (§9 transport) + named pipes; `svchost` equivalent with per-service SIDs; dependency/order engine; failure-action engine → **maps directly onto Linux restart policies *only* as a bottom layer; the Windows-facing semantics live in services.exe**.
- **systemd relationship (must not break Ubuntu):** the *host* boot remains systemd. We add one systemd unit `winpersonality-services.service` (user-session-scoped per logged-in seat + one system-scope instance for session 0 analog). Services.exe is a *child* of the personality boot order — a guest, never a replacement of PID 1, `systemd-logind`, D-Bus, or networking managers. On shutdown, systemd kills services.exe → personality service stop-ordering applies within our subtree. The `sc.exe`/`net start` PE CLIs talk to services.exe; `systemctl` users see exactly what stock Ubuntu sees (LINUXR witness test).
- Trap list: `SERVICE_INTERACTIVE_PROCESS` (pre-Vista) must fail creation like Vista+; `QueryServiceConfig2`/`DESCRIPTION`/`PRESHUTDOWN` ordering; `SERVICE_PAUSED` state machine (`SEND_CTRL_PAUSE_CONTINUE` requires handler); session-0 apps silently *cannot* create visible windows (UIPI/window-station check — cross-dep GFX); `CreateService` writes registry + hive ACL (our registry, our `winsec`); service sideloading from `Parameters\ServiceDll`; SCM database ACL (`NT SERVICE\` group access rights).

## 6. Networking (Winsock / AFD / IOCP / WFP / pipes)

**Core decision:** Winsock is a **kernel-adjacent** stack on NT: `ws2_32.dll` → `afd.sys` (socket file objects) + `nsi.sys` (interface/route info) + base objects (events, semaphores, **IOCP**). The ARCH DoD (kill-helpers test; ≤0.05 host-syscall/NT-call) **forbids** a user-mode Winsock server → the socket personality must live in the kernel, as a new filesystem-on-sockets: **`ntafd` kernel module binding PF_INET/PF_INET6/PF_UNIX `struct file`s into the NT object namespace** with NT semantics layered on Linux sockets (DIRECT substrate, ADAPT layer).

Faithful points (each has a concrete implementation):
- **Socket-as-file**: NT sockets are FILE_OBJECTs → `ReadFile/WriteFile/DeviceIoControl(WSAID_*)` on a socket handle; `NtDeviceIoControlFile` with AFD's tdi-internal opcodes; `WSAIoctl` giant switch (`SIO_GET_EXTENSION_FUNCTION_POINTER`, `SIO_ADDRESS_LIST_CHANGE`→event, `SIO_RCVALL`→needs promiscuous: `CAP_NET_RAW` bridge, `TCP_NODELAY`…). **NEW-KERNEL**: AFD's non-blocking + select/poll model differs from BSD: `connect()` in-flight returns `WSAEWOULDBLOCK` + `select(write_ready)` semantics; `WSAEALREADY` vs `WSAEISCONN` on repeat connects; UDP `connect()`+implicit-bind flow; zero-byte send keepalives; `SIO_KEEPALIVE_VALS` per-socket timers (Linux has `TCP_KEEPCNT` etc. — ADAPT, exact `WSAIoctl`-style event on failure: `afd!AFD_EVENT` → **kernel must signal an event object on TCP_USER_TIMEOUT/keepalive failure** — new kernel hook).
- **Error codes**: `WSAGetLastError` domain (10038…) must be produced by a **status→WSA mapping table inside ntafd/ntdll on our own NTSTATUS values — errno must never leak**. e.g. our kernel's connect-fail status list → WSAECONNREFUSED etc. (The DoD's "gaps return correct error codes" applies doubly here: 90+ WSA codes, several unreachable-but-required shapes: `WSASYSCALLFAILURE` only when the *syscall itself* errors — meaning our syscall layer must distinguish "transport error" vs "kernel-layer error" — a design point for ntafd return codes.)
- **IOCP**: NEW-KERNEL object `NtCreateIoCompletion` + `NtGetQueuedCompletionStatus` with exact semantics: per-I/O single completion packet (`OVERLAPPED` completion key + bytes + `pOverlapped`), **wait-timeout=0 polling quirks**, `RemoveIoCompletion` cancellation, priority boost on completion (map to our wait runtime), key-per-handle, and the requirement that *files, pipes, mailslots, AFD sockets, our `.sys` device handles* can all be `BindIoCompletionCallback`-able → design rule: **any personality handle can post NTSTATUS completions to an attached port**; implement as generic completion channel in the object manager (shared with §2 IRP completion — same machinery; this is the single biggest NEW-KERNEL item of §6 and pays for itself across async file/driver/network).
- **AFD event model for WSAEventSelect**: socket state → WSAEVENT auto-reset events (`FD_READ/FD_WRITE/FD_CLOSE/FD_CONNECT…`) — requires kernel socket→event binding: `ntafd` attaches our KEVENT objects on `sk_data_ready`/`sk_state_change` callbacks (existing Linux notifier infra; ADAPT with new plumbing).
- **WFP (Windows Filtering Platform)**: sublayer/weight/condition ALE-layer model with callouts — Linux netfilter/nftables/eBPF cannot present WFP's *API* (enumerate filters, session-level conditions like AppContainer SID — §1, `FWP_ACTION_PERMIT` granularity, ALE_AUTH_CONNECT/RECEIVE_* layers that gate *pre-connect* and carry *process identity*). **NEW-KERNEL**: a filter engine keyed on (process token, 5-tuple, FWP conditions) hooked at Linux `nf_hook` + `connect()`/`bind()` in ntafd; WFP user-mode API ([MS-FWPM] partially documented + extensively RE'd; EXT-DOC+EXT-RE) served by this engine. Needed for: appcontainer lockdown (§1), firewalls, and several AC/DRM products' telemetry.
- **Named pipes**: `\pipe\*` device: message+byte mode, `ConnectNamedPipe` with `FILE_FLAG_OVERLAPPED`→IOCP, **`ImpersonateNamedPipeClient`** (§1 kernel impersonation), `PeekNamedPipe`, `TransceiveNamedPipe` — all NT object semantics; transport: in-host pipes = kernel-object pairs over a unix-socket-ish (DIRECT substrate); **pipes-over-SMB** (`\\server\pipe\x`) requires SMB2/3 client: implement [MS-SMB2] (open spec, EXT-DOC; Samba libs *may* be used for the SMB wire stack in the *user-mode redirector* without touching the execution path — SBOM provenance check first, or write our own).
- **Name resolution**: Winsock resolver behaves like `dnsapi.dll` in-proc: DnsQueryEx types (SRV/A/AAAA/… + `DnsQuery_UTF8` semantics), suffix search from ip config, hosts file order (Lmhosts/NetBIOS historically — modern mostly DNS + `getaddrinfo`-shaped `NSP` providers); NT's async resolver integrates with waitables (`WSALookupServiceBegin` on NSI) → implement resolver in ntdll talking to nsi-shim + real DNS over our sockets (DIRECT); `ipconfig`/`GetAdaptersInfo/Addresses`/`GetIfTable2` families (iphlpapi): nla/netlink ADAPT, careful with the `Addresses`/`DnsServer`/`Gateways`/LLMNR/NCSI fields ACs and Steam read.
- **Misc**: WSAStartup refcount per-process + version negotiation; `SO_EXCLUSIVEADDRUSE` (NEW-KERNEL: enforceable in our ntafd pre-bind check — Linux has no equivalent; must implement "deny future binds while held" via kernel hook); `WSA_FLAG_OVERLAPPED` on WSASocket pairs with `AFD` handle attributes; multicast `IP_ADD_MEMBERSHIP` interface-index model; `GetAcceptExSockaddrs`/`AcceptEx`/`TransmitFile`/`DisassociateCurrentThreadFromPort` extension functions (AFD-specific kernel ops, documented by behavior).

## 7. Audio (WASAPI / audio engine / ASIO)

**Substrate reality:** Ubuntu 26.04 ships PipeWire (ALSA/JACK). The Windows *architecture* is: `audiosrv` (user-mode **audio engine**, a session-0/1 mix engine, APOs in-proc-com) + `AUDIOKSE.sys` + port class drivers; WASAPI shared mode = client pulls/pushes into per-endpoint float32 mix with engine-owned **resampler + volume (per-endpoint + session) + effect chain**; event-driven pacing via `GetNextPacketSize` + `IAudioClient::GetService(PACKET_VOLUME…)`; exclusive mode = client owns the endpoint (hardware formats, event callback, `SetMaximumFrameLatency`).

**Faithful design (kernel/user split):**
- Keep the **audio engine user-mode** (`audiosrv` personality service — faithful to NT, allowed by kill-helpers rule since audio is not on the launch path): our `AudioSrv` builds sessions over a **PipeWire-native or direct-ALSA backend**. Latency math: WASAPI shared typically adds 2 engine periods (~3–10ms); PipeWire graph already does per-client quantum; mapping our client ring buffer + `GetNextPacketSize` accounting onto PipeWire's `process()` callback = **ADAPT, no extra copy if we import the client's ring as a PipeWire memfd buffer (zero-copy shared buffer objects are PipeWire-native)**. Event signaling: client `MMDevice::Activate` gets a kernel **event** signaled on packet-boundary — **NEW-KERNEL glue**: PipeWire's fd readability → our `KeSetEvent` via a small in-kernel `winmmio`-style fd-signaler? Simplest faithful design: the client waits on *our base event object*; audiosrv signals it from process-thread — but kill-helpers forbids audiosrv on the launch path, *not* on the audio path; a dead audiosrv may legitimately fail audio (like Windows). Decision: **user-mode pacing thread inside our `audiosrv` signals kernel events** → allowed and matches NT. Shared-mode latency target ≤ current Windows +1ms; measurable with loopback.
- **Endpoint enumeration** (`MMDeviceEnumerator`, default-device-change notifications, `eRender/eCapture`, role `Multimedia/Communications/Console`): map to PipeWire nodes + `si-audio-adapter`/A2DP via our own policy daemon; change notifications must preserve `IMMNotificationClient` ordering/flags (device-gone vs disabled).
- **Exclusive mode + ASIO**: `AUDCLNT_SHAREMODE_EXCLUSIVE` must *steal* the device: audiosrv suspends the PipeWire node, hands the client an ALSA `hw:` handle through our `winaudio` personality shim (kernel: `snd_pcm` direct with `SNDRV_PCM_IOCTL_*`→ our WASAPI position/clock APIs). `IAudioRenderClient::GetBuffer` position clocking = ALSA `snd_pcm_avail/hw_ptr` — ADAPT; `GetDefaultDevicePeriod` must report the *real* negotiated period. ASIO vendor DLLs are in-process PEs calling WASAPI/WDM — they work *if* exclusive path is exact. This (exclusive + event-driven, no resampler in path) is the latency-critical deliverable; experiment = pro-audio app loopback round-trip vs Windows baseline.
- **KSPROXY/portcls, `AUDIOENDPOINT` driver stack**: only as far as our own first-party `.sys` (the DoD's virtual-audio device) — do not attempt third-party audio `.sys`.
- Traps: volume-boost>1.0 semantics, per-session `IAudioSessionManager2` (session creation order = process start, session-disconnected cleanup), **WASAPI loopback capture** (`KSAUDIO` duplicate-mode: needed by OBS/Discord — implement as PipeWire monitor node surfaced as a capture endpoint with `GetDefaultPacketSize` matching the render format exactly), event-driven "silence-packet" pacing, `AUDCLNT_E_BUFFER_SIZE_NOT_ALIGNED` negotiation dance, `IAudioTimingEngine`? (no — `IAudioClock2` via QPC↔PCM-frame anchor linearity), MMCSS priority.

## 8. Input (raw input / DirectInput / XInput / HID / hooks)

- **Raw input** (`RegisterRawInputDevices`, `WM_INPUT`, per-device `RID` headers, joystick HID reports): evdev/hidraw already delivers the *same byte streams* the HID reports carry → **ADAPT**: an input daemon (or better: in the window-server process, cross-dep GFX) keeps a device registry, parses reports per HID descriptor (same data Windows' `hidclass` parses — [HID1.11] public), forwards `RAWINPUT` packets; `GetRawInputDeviceInfoW` descriptors from real HID report descriptors via `/sys/.../device/descriptor` (DIRECT). Device-add/remove → `WM_INPUT` RIM_TYPEDEVICE add/remove ordering + `GetRawInputDeviceList` flags (RIDEV_ flags, `hidupi` page/usage).
- **XInput** (fixed-slot Xbox pad abstraction, `XInputGetState`, vibration): implement atop raw input + `ff-memless` evdev force-feedback output (`XINPUT_VIBRATION` → FF_RUMBLE) — DIRECT; slot-numbering/ordering stability is the trap (device hotplug must not renumber mid-game like Windows' "slot taken by another user" states).
- **DirectInput**: enumerate same devices; effects (`DIEffect` envelope/condition/periodic) → Linux FF effects where expressible, **ADAPT** with honest `DIERR_UNSUPPORTED` for non-expressible envelopes (many games probe). `SetCooperativeLevel` exclusive-mode = grabs device from OS cursor (needs window-server coordination).
- **Keyboard**: `GetAsyncKeyState`/`GetKeyState` semantics (sign bit high = pressed since last poll — **kernel-maintained key-state ledger**, NEW-KERNEL if the WM owns it), dead keys/IME (GFX agent), scan-code sets (raw input gives `MakeCode`; `MapVirtualKey` tables — EXT-DOC), repeat-rate from our settings bridge.
- **Hooks** (`SetWindowsHookEx` WH_KEYBOARD_LL/WH_MOUSE_LL with 300ms timeout + `HC_ACTION` ordering; `SendInput` UIPI gate on IL — §1): these live in the window subsystem; the LL-hook chain must run in *the installing thread's* pump with NT's timeout kill semantics (hook removal + `GetLastError` shape). Cross-dep: GFX agent — but note the **security hooks belong to §1** (`inputInject` capability, IL check) and the **low-level timing** (inject path must not add frames of latency: inject → evdev-mirror inside window server's input thread; evdev UINPUT is DIRECT).
- **Mouse**: raw-mode (`RIM_TYPEMOUSE` usFlags MOUREMBEDDED/ABSOLUTE), accel off in raw mode (games use raw only) — trivial; but `SPI_GETMOUSEACCELERATION` must *truthfully* report (ACs/UIPI? no, Steam overlay does).

## 9. COM

Windows COM is entirely **user-mode** (RPC in the ALPC/named-pipe transports) — a native personality COM is the *faithful* architecture (no Wine-style bridge exists in NT either; `combase.dll`/`ole32` are OS components).

- **Class store**: `HKCR\CLSID\{...}\InprocServer32/LocalServer32/…`, `AppID`, type-lib registration → our registry (§ REG agent) with SDs (§1). `DllRegisterServer` self-reg works once our reg+PE loader land.
- **Activation**: `CoCreateInstance` → class cache → in-proc (`LoadLibrary` our PE loader) / local 32 (create process w/ `CoInitializeSecurity`-shaped args) / out-of-proc (DCOM activation via `SCM`-side activation server over [MS-ORPC]/DCOM `IRemoteSCMActivator` on our LRPC transport).
- **Apartments**: STA = thread message queue (window server cross-dep: STA pumping rides the same message loop machinery; `CoWaitForMultipleHandles` merges COM+msg waits → our waitable-object wait runtime (§2 `KeWaitForSingleObject` engine reused in UM via `MsgWaitForMultipleObjectsEx`) — this is where kernel objects genuinely help); MTA = RPC-thread pool with refcounting (neutral); `ApartmentType`/`CtxClass` cross-apartment marshalling; reentrancy semantics (STA inbound call during `IMarshal` round-trips) are the subtle part — need the ORPC *call* model (cancel, ping, `ORPC_ACTIVATE_FLAGS`) not just "function calls".
- **Marshalling**: proxies/stubs (`ProxyStub DLLs` ship with apps; `oleaut32`/`Ole32`-generic marshaler for IDispatch/VARIANT), `IMarshal`, `CoTaskMemAlloc` rules, `SAFEARRAY`/`VARIANT` ABI (EXT-DOC — Microsoft publishes `[MS-OAUT]`/proxy format; classic proxy data from typelibs), `GetProcAddrOf`… Interface marshalling *data* format `[MS-ORPC]` is specified → implement reader/writer engine DIRECT (large but spec'd).
- **Transports**: `SequenceEndpoint` = **LRPC** over our ALPC-equivalent (**NEW-KERNEL-ish**: our base IPC ports (§6/§2 object manager) provide bidirectional message ports; Windows LRPC semantics (`RpcBinding*`, shared-memory transfers for large buffers, `NCALRPC` endp names under `\RPC Control\`) map to our port objects + section (§MEM agent) shared-memory transfer — the kernel contribution is the port+section transfer, which we need anyway for named pipes). DCOM/TCP (`nettcpbinding`? no — `135` EPMapper + dynamic ports, `[DCOM]` activation over TCP) for cross-machine: implement EPM + `[MS-RPCE]` NDR transfer syntax (NDR format strings documented; NDR64 less so — EXT-RE).
- **Scope judgment for games/apps**: (a) in-proc COM everywhere (DX components! `D3D11CreateDevice` returns COM objects — the GFX agent's APIs are COM *structurally*, so apartment/refcount/VTable correctness is on the critical path of nearly everything — schedule COM core with GFX); (b) out-of-proc/DCOM: needed by Office-class apps and some AC/DRM IPC — defer full [MS-ORPC] to phase 3; (c) WinRT (`RoInitialize`, `IInspectable`, activation over RoApi + AppContainer tokens §1) — same transport, add `pwinmetalib`/metadata reader; flag as separate phase (matches UWP DoD domain).
- Traps: `CoInitializeEx` failure codes/reinit counts, `CoUninitialize` reentrancy, `CO_E_TPRIVATE_?` … `RPC_E_CHANGED_MODE`, MTA-thread-pool min/max (`CoIncrementMTAUsage`), `CoMarshalInterThreadInterfaceInStream` + `GetNextMessage` STA ordering, `IMethodCallMessage` legacy `IMarshal`-free .NET remoting hooks (§10 interop), apartment-thread-windowless hooks, `STGM_?`/`IOleInPlaceActiveObject`? (Ole UI → GFX/INP surface, note dependency).

## 10. .NET

**Structure recap:** managed app (`.exe` apphost PE + `.dll` IL assemblies; `PE/CLI` metadata: CIL headers, metadata root, #Strings/#Blob/#US heaps, tables) → `hostfxr→hostpolicy→coreclr.dll` → **CoreCLR** = {PAL | gc | jit (RyuJIT) | EE (class loader, exception mgmt, interop) | threadpool (IOCP-based!)}. .NET Framework 4.x = closed-source `clr.dll`+`wclr`, redistributable, requires Win7+ API level.

**Portability facts (decisive for strategy):** CoreCLR is MIT-licensed and **already runs on Linux natively (ELF)** — i.e. the *managed runtime itself is portable source*. The interesting question is therefore not "port .NET" but "what runs, and through which door":

| Path | What executes | Requires from our personality | Status |
|---|---|---|---|

(uses NT events), `LoadLibrary`+`GetProcAddress` (used for OS feature probing), TLS, `GetLastError`, `Rtl*` (memory/hash), IO: Winsock+file+IOCP (`ThreadPool` uses IOCP) | **EASIEST credible win** — pure personality fidelity, no runtime porting at all |
| **B. .NET 8+ apps under our PE path executing the *Microsoft-built Windows* `coreclr.dll`** (real PE DLLs, self-contained installs) | genuine Windows binaries incl. **What the CLR needs from the OS (explicit list)**: commit-able virtual memory with page-state machine; per-process address-layout determinism (GC heap uses reserved regions; `MEM_RESERVE` gaps matter); threads + TLS (`TCBEDS_` + `TlsAlloc`, and Windows x64 TEB in `CONTEXT` for exception dispatch), table-based SEH with **correct second-pass semantics and `CONTEXT` fidelity** (RyuJIT's GC-info-based stack walking consumes the `CONTEXT` our dispatcher builds — a wrong `Rsp/Rip` fixup = corruption), futex-grade waits + IOCP for the pool, sections for `MemoryMappedFiles` and assembly sharing, high-resolution monotonic time + `GetSystemTimePreciseAsFileTime`, `SetProcessWorkingSetSize` (GC tries), `QueryMemoryResourceNotification` (GC low-memory mode — DIRECT: pressure info), perf counters (`PERF_COUNTER_*` for `EventCounters` — PDH ADAPT), and **loader-lock/`DllMain` ordering fidelity** (`FreeLibrary` while threads in-flight: refcount semantics of our loader gate the whole design).

**Fastest credible order:** A (NativeAOT) → B (CoreCLR 8/9/10 PE + our Win32) → interop-dependent parts of C. Managed *libraries* (System.*) need nothing from us — they run on top of the PE coreclr. Resolving experiment for uncertainty in path B: run `hello-world` .NET 8 self-contained publish under a mature-enough ntdll/loader/exception stub, trace `ntdll` exports requested; publish the delta (this is the single best *fidelity barometer* for the whole project because .NET hits nearly every personality subsystem).

Traps: exception `HRESULT`/stack-trace string parity (Watson off), `Environment.OSVersion`/`RuntimeInformation.OSDescription` (apps branch on it — we must declare our compat persona deliberately, §3 U-13), `System.Security.Cryptography` uses **CNG/BCrypt/NCrypt + OS certificate stores** (`bcryptprimitives.dll` on Win11 is a *lower*, still-NT-ABI DLL — we implement bcrypt/ncrypt atop OpenSSL as our personality component + cert store from our registry/LSA §1), `Console` host protocol (`ReadConsoleInputW` — INP/GFX), `FileSystemWatcher` needs our registry/dir-notification facility (ReadDirectoryChangesW = kernel change-notify — NEW-KERNEL shared with FS agent), AppContext config via `*.runtimeconfig.json` (pure UM).

## 12. Kernel vs user-space split (justified)

**In the kernel** (each is either NT-kernel-resident, or needed on the launch/syscall path, or requires privileged state):
personality syscall table + object manager (processes/threads/sections/events/semaphores/mutants/timers/ALPC-ports/**IOCP**/tokens), `winsec` (AccessCheck/SD/SID/IL/capability), impersonation plumbing, `ntafd` + completion engine + WFP engine + pipe impersonation, IRQL/SEH/unwind runtime + device-stack/IRP engine (for NT-ABI `.sys`), session objects, key-state ledger hooks.
Justification: ARCH DoD kills user-mode helpers on the launch path and budgets ≤0.05 host syscalls/NT call → any of these in user mode is disqualifying; also NT itself has them in kernel (faithfulness + security: a user-mode security server is the Wine/CSRSS-as-translation pattern).
**In user-space** (each is NT-user-mode by design — putting them in kernel would be *less* faithful): `services.exe`/`svchost`/SCM, LSA/SID-name/privilege policy, `audiosrv` engine + APO host, window/input server (GFX agent), COM (`combase`+ORPC marshalling), DnsQuery/resolver in ntdll, bcrypt/ncrypt providers (crypto is DLL-level on NT), PDH/WMI-lite providers, `consent` elevation broker, SMB redirector (MRxSmb2 as UM FS driver is *less* faithful; do it as our own in-kernel redirector only if the FS agent's design demands — uncertainty noted in R-6 below).

## 13. Deliverables roll-up

### 13.1 Proposed architecture (this domain)

```
 PE process ─ ntdll (SSN-numbered syscalls, SEH/VEH, resolver, COM base)
   │ personality syscall layer (index-compatible SSDT incl. win32k range)
 ├─ KERNEL
 │   objmgr: tokens+SD+SeAccessCheck(winsec) · waits · IOCP/completions · sections ·
 │           ports(ALPC/LRPC) · pipes(+impersonate) · sessions · ntafd(sockets,WFP,ipcp) ·
 │           NtosHal exec layer: IRQL runtime · PE-in-kernel loader · .pdata unwind/SEH ·
 │           device stack/IRP/DPC/MDL · CI(test-signing DSE)          ← our own NT-ABI .sys run here
 ├─ USER (personality services, systemd-scoped, launch-path-independent)
 │   services.exe(SCM) · svchost(s) · audiosrv(WASAPI engine⇄PipeWire) ·
 │   winstation/input server(GFX agent; raw input/XInput/hook chain) ·
 │   COM/ORPC runtime · LSA(SID store, elevation, bcrypt/ncrypt) · PDH/WMI-lite ·
 │   consent(UAC UI) · our test-AC demo stack (attestation w/ project CA)
 └─ LINUX base untouched: systemd, PipeWire, evdev, netfilter(under ntafd), /dev/tpmrm0,
     ext4 xattrs, namespaces for containment — never replaced, never weakened.
```

### 13.2 Testing methodology (this domain)
1. **Differential oracle**: a reference Windows 11 VM (allowed as *test oracle only* — never in the SUT execution path) + scripted API probes recording return codes/info-class bytes; publish deltas; gate: zero divergence on P0 classes.
2. **Golden vectors**: SID canonicalization + capability-SID hashing test-vectors; WSA↔status mapping table unit tests; NDR/MS-ORPC round-trip vectors from [MS-NDR].
3. **Security fuzzing**: `SeAccessCheck` table-exhaustive (all ACE kinds × privileges × IL × capability) vs a reference model (independent implementation, e.g. Python) — a TLA-style model for token filters.
4. **Driver conformance**: Toaster sample suite (MS public), IRQL assertion harness (drivers instrumented to call our `RtlpCheckIrql` probe), DPC latency stress, exception-table torture tests, our-test-CA load path (DOD-DRV-A002), + **attempt-matrix audit** for DOD-DRV-A001 (log exact failure reasons: unresolved import, layout probe, signature).
5. **AC/DRM**: our own test-AC (UM + first-party kernel driver) exercising K-01..K-11 mechanisms end-to-end against a mock server; Denuvo-free commercial corpora for packer paths; per-check *honest-failure* tests (gated criteria must fail *closed and clean*, never partially).
6. **Latency**: audio round-trip vs Windows baseline on same HW; input path event→queue timestamps; IOCP wakeup latency vs Windows (±20%).
7. **Regression**: Ubuntu witness image (DoD LINUXR) with `winsec`/`ntafd` modules loaded-but-unused → zero behavioral deltas in systemd/PW/NetworkManager/journal golden logs.

### 13.3 Implementation order (this domain; parallelizable tracks marked ∥)
1. **Token + winsec + base-object security** (blocks: object manager users, services, pipes, COM-sec, UIPI).
2. **IOCP/completion engine ∥ ntafd core (blocking+non-blocking socket semantics + WSA error mapping)** → enables Steam-class netgames and .NET threadpool.
3. **Exception/unwind runtime (UM ntdll first, kernel `.pdata` second)** — shared by drivers, .NET, AC U-08.
4. **Pipes+impersonation → LRPC ports → COM in-proc/out-of-proc ∥ SCM/services.exe** (services depend on tokens+LRPC; COM on pipes+registry).
5. **Audio engine (shared→exclusive)** ∥ **Input (raw/XInput)**.
6. **NtosHal driver host + our virtual-device stack + test-signing CI** (needs 1,3,4).
7. **WFP engine + AppContainer/capability gates** (needs 1,2).
8. **.NET paths A→B**, PDH, bcrypt/ncrypt (needs 1–4, FS dir-notify).
9. **Our test-AC end-to-end + attestation story**; publish third-party AC/DRM capability matrix with honest GATED rows.

### 13.4 Technical risks (top)
- **R-AC-1 (existential, accepted):** kernel-AC/MS-attestation titles are permanently GATED (K-12). Mitigation = scope declaration + vendor certification program + our test-AC proves mechanisms.
- **R-DRV-1:** third-party `.sys` in host kernel = Linux-regression violation vector; even our own drivers can panic Ubuntu. Mitigation: driver crash = driver isolation (kill device stack, unload, *never* panic); long-term research: in-kernel fault domain (or CFI+KASAN-hardened build) + keep external surface first-party-only.
- **R-SEC-2:** `SeAccessCheck`/token bugs = privilege mis-grants in *both* worlds (a PE sandbox escaping into Linux uid space). Mitigation: PE processes never gain POSIX rights from tokens (§1.4 rule 1) — check-reduce blast radius to data, not root.
- **R-NET-1:** AFD semantic depth (keepalive events, AcceptEx, WSAEALREADY corners) underestimation → games break subtly. Mitigation: differential corpus tests with 10 real netgames on IOCP paths.
- **R-NET/COM-2 (uncertainty):** SMB redirector kernel-vs-user placement and WFP condition coverage: resolving experiment = run 2 titles that use named pipes over `\\.\pipe` vs `\\host\pipe` + 1 firewall-product probe.
- **R-DOT-1:** closed `clr.dll` (.NET FW) probes undocumented ntdll internals; may be unfixable beyond stubs. Resolving experiment in §10.
- **R-PRV-1:** exact `coreclr.dll`/`ntdll` binary distribution rights (using *MS's own binaries* is a license question: redistributing .NET Windows binaries is MIT-permitted for CoreCLR; *Framework* is redist-licensed; ntdll itself is not redistributable → our ntdll is our own implementation (already project-wide assumption, restate for legal).
- **R-PRV-2:** anti-cheat/DRM *circumvention-law* exposure if anything is framed as defeating their checks. Policy: faithful-implementation-only, honest-failure, documented in every gate.
- **R-AUD-1:** shared-mode latency/loopback parity unproven with PipeWire graph; resolving experiment: zero-copy WASAPI⇄PipeWire ring prototype on the target hardware.

### 13.5 Known compatibility traps (cross-referenced inline; short list)
SSN/build drift (U-05/06), QPC-vs-TSC monotonic edge (U-07), exception first-pass ordering (§10), IOCP completion-on-cancel rules (§6), WSAEINPROGRESS/WSAEALREADY sequences (§6), SO_EXCLUSIVEADDRUSE race window (§6), pipe impersonation levels + `PIPE_REJECT_REMOTE_CLIENTS` (§5/§6), session-0 invisibility vs legacy installers (§5), dependent-service pending-state tick timeout (§5), WASAPI aligned-buffer retry dance (§7), XInput slot stability (§8), STA reentrancy + `CoWaitForMultipleHandles` timeouts (§9), GC↔`VirtualAlloc` state-machine expectations + `SetProcessWorkingSetSize` (§10), ACL canonicalization + inheritance-at-create (§1), capability-SID hash exactness (§1), `GetTokenInformation` undocumented classes (§1, EXT-RE), WMI dependency of some .NET apps (§10).

### 13.6 Original implementation required (no usable open source exists)
In-kernel NT token/`SeAccessCheck` engine; NT object manager w/ completion ports (ours, co-designed w/ ARCH domain); `ntafd`+IOCP; WFP engine; IRQL/`Ke*`/`Ex*`/`Io*` executive + kernel PE/SEH host (`NtosHal`); `ci.dll`-analogue; LRPC/ORPC marshalling engines (specs exist, code does not); WASAPI event pacing on PipeWire; raw-input RID layer; our CA/attestation stack + test-AC; SC-manager engine per [MS-SCM]; bcrypt/ncrypt+cert-store providers; PDH.
